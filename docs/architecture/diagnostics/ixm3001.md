# IXM3001: service operation must return FluentResults

## Trigger

The rule activates only when `FluentResults.Result`, `FluentResults.Result<T>`, `Task<T>`, and `ValueTask<T>` resolve in the compilation. When those approved return symbols are available, an externally visible ordinary method declared by a service type must use an approved result shape.

## Rationale

Externally visible service operations expose expected success and failure to callers. `Result` or `Result<T>`, directly or in `Task` or `ValueTask`, keeps that outcome explicit and transport-neutral.

## Noncompliant example

```csharp
public interface IOperationService
{
    ValueTask<OperationResult> ExecuteAsync(OperationRequest request);
}
```

## Compliant example

```csharp
public interface IOperationService
{
    ValueTask<Result<OperationResult>> ExecuteAsync(OperationRequest request);
}
```

## Required shape

The service contract must return `FluentResults.Result`, `FluentResults.Result<T>`, `Task<FluentResults.Result>`, `Task<FluentResults.Result<T>>`, `ValueTask<FluentResults.Result>`, or `ValueTask<FluentResults.Result<T>>`. The interface declaration owns the report; an implementation is not reported again unless it exposes an additional public service operation.

## Remediation and suppression

Return an approved FluentResults shape. Treat a change to an existing public raw return type as a breaking API migration. If the approved FluentResults return symbols are absent, the rule does not activate; do not use suppression to conceal an active, unsupported service return shape.

## Review boundary

The analyzer checks return shapes, not business semantics. Review whether failures are expected and whether changing an existing raw public return type is a breaking API migration.
