# IXM3002: business failure must use a coded error

## Trigger

The rule analyzes direct FluentResults failure creation unless `IXModularityProjectRole` is `Test`, `ArchitectureTest`, `Analyzer`, or `SourceGenerator` (case-insensitive). Those four roles are excluded from IXM3002 analysis.

## Rationale

Stable typed errors let callers distinguish expected failures without parsing mutable messages or coupling a reusable library to a transport.

## Required error contract

A concrete business error derives from `FluentResults.Error` and owns a `public const string Code` whose value uses lowercase snake case. The rule rejects string-only failure calls, direct use of base `Error`, invalid or missing codes, and `Result.Try`. Preserve all meaningful errors on a failed result.

## Noncompliant and compliant examples

```csharp
// Noncompliant: the direct failure has no stable coded error.
return Result.Fail("The operation cannot continue.");

// Compliant: OperationUnavailableError derives from Error and owns
// public const string Code = "operation_unavailable".
return Result.Fail(new OperationUnavailableError());
```

## Review boundary

The analyzer validates direct statically visible construction. Review indirect factories, message safety, sensitive information, code ownership, and whether the failure is actually expected. A narrow suppression is only for an unprovable safe construction; it is not needed for one of the four excluded project roles because IXM3002 does not analyze those roles.
