# IXM1004: public service type requires complete XML documentation

## Trigger

The rule applies to an externally visible, user-authored type whose name ends in `Service`, or to any such type implementing or deriving from an interface named `I*Service`. It reports the service type when its XML documentation is incomplete.

## Rationale

A public service type exposes behavior, state, and lifecycle choices that names cannot fully convey. Its documentation anchors the intended responsibility and prevents consumers from binding to incidental implementation details.

## Noncompliant example

```csharp
public interface IOperationService
{
}

public sealed class OperationCoordinator : IOperationService
{
}
```

`OperationCoordinator` is a service because it implements `IOperationService`, even though its own name does not end in `Service`.

## Compliant example

```csharp
/// <summary>Coordinates validation and execution of a library operation.</summary>
public sealed class OperationService
{
}
```

## Remediation

Add a non-empty `<summary>` and documentation for every applicable generic type parameter to both service types named `*Service` and types classified as services through their `I*Service` interfaces.

## Exceptions

The rule applies to user-authored public service types, not generated types, framework-derived scaffolding, or internal helpers. A service type that is too difficult to summarize may have more than one responsibility; follow the [design-principles](../design-principles.md) review rules.

## Suppression

The analyzer defaults to warning and repository policy sets error. Suppress only a specific declaration with a compatibility justification, owner, and review date; never suppress the entire diagnostic category.
